# TradePilot UX 정의서 v0.2

> 작성: 한병준 (PM·프런트엔드) / 2026.11.27 / 상태: 초안 (12.03 설계 확정 전 팀 검토용)
> 근거: 기획서 v0.1 (FR-01~04, 성공 기준), 설계서 v0.1 (1장 입출력, 5장 번역 규칙, 7장 프런트엔드, 8장 테스트), 계획서 v0.1 (W-10, 11.26 결정 사항)
> 이 문서는 **기능(UX)** 만 정한다. 시각 디자인(UI)은 별도 프로토타입과 디자인 시스템 문서에서 다룬다.

## 1. 설계 원칙

| # | 원칙 | 화면에서의 뜻 |
| --- | --- | --- |
| P1 | **숫자는 문서 그대로** | 금액·날짜·수량은 코드가 검증한 값만 보여 준다. 표와 해설의 숫자는 항상 같다. AI가 만든 숫자는 없다. |
| P2 | **이상한 것부터 먼저** | 검산 불일치·누락이 있으면 결과 화면 맨 위에서 가장 먼저 보인다. 문제가 없으면 조용히 "검산 통과"만 표시한다. |
| P3 | **원문과 나란히** | 모든 결과는 원문 이미지 옆에서 대조할 수 있다. 사용자가 AI를 믿지 않아도 직접 확인할 수 있어야 한다. |
| P4 | **AI가 쓴 글은 표시한다** | 문서에서 읽은 값(표)과 AI가 쓴 글(해설·번역 문장·체크리스트)을 시각적으로 구분한다. |
| P5 | **다음 행동은 하나** | 모든 화면에는 가장 중요한 버튼이 하나만 있다. 오류 화면도 "무엇을 하면 되는지"로 끝난다. |
| P6 | **무역 용어는 그 자리에서 푼다** | 용어를 찾으러 다른 곳에 가지 않게, 용어가 나온 자리에서 설명을 보여 준다. |

## 2. 사용자와 사용 맥락

- **사용자**: 무역 전담 인력이 없는 국내 중소기업 실무자. 영어는 읽지만 Incoterms·결제 조건 같은 무역 용어는 모른다.
- **사용 환경**: 사무실 데스크톱(1280px 이상) 우선. 노트북(1024px)에서도 깨지지 않아야 한다. 모바일은 MVP 범위 밖이지만 결과 확인은 가능하게 한 열로 쌓는다.
- **사용 빈도**: 월 25건 내외(기획서 가정). 매번 처음 쓰는 사람처럼 설명 없이 쓸 수 있어야 한다.
- **핵심 질문 3개**: ① 이 서류가 무슨 내용인가 ② 얼마를, 언제까지, 어디로 보내야 하나 ③ 누가 무엇을 해야 하나

## 3. 정보 구조와 화면 흐름

### 3.1 화면 목록

| ID | 화면 | 진입 조건 | 주요 행동 |
| --- | --- | --- | --- |
| S1 | 시작·업로드 | 서비스 첫 접속, "새 문서" | 파일 올리기, 예시 문서로 체험 |
| S2 | 처리 중 | 업로드 성공 | 기다리기, 취소 |
| S3 | 결과 | 처리 완료 | 확인 필요 확인, 원문 대조, 해설 읽기, 체크리스트 확인 |
| S4 | 오류 | 업로드 전 검증 실패 또는 처리 실패 | 다시 올리기, 다시 시도, 예시로 체험 |

> **결정: 시작 화면과 업로드 화면을 하나로 합친다.** 설계서 7장은 둘을 나눴지만, 시작 화면의 목적("사용자가 스스로 업로드 시작")은 업로드 영역이 첫 화면에 바로 있을 때 가장 잘 달성된다. 클릭이 한 번 줄고, remove.bg·Mercury 같은 업로드 중심 서비스도 같은 방식을 쓴다.

### 3.2 흐름

```
S1 시작·업로드 ──(파일 선택: 형식·용량 통과)──▶ [분석 시작] ──▶ S2 처리 중 ──(완료)──▶ S3 결과
     │                                                        │                     │
     ├─(형식·용량 실패) → S1 안에서 인라인 오류                ├─(취소) → S1          └─[새 문서] → S1
     └─[예시 문서] ─────────────────────────────────────────▶ S2 (예시 데이터)
                                                              └─(판독 불가·문서 종류 아님·시간 초과·서버 오류) → S4 → [다시 올리기] → S1
```

### 3.3 결과 화면(S3) 읽는 순서

결과 화면은 한 페이지이며, 사용자의 질문 순서대로 위에서 아래로 놓는다.

1. **무슨 문서인가** → 상단 요약 (문서 종류, 당사자, 총액, 핵심 기한)
2. **이상한 곳은 없나** → 확인 필요 배너
3. **무슨 뜻인가** → 쉬운 해설 + 용어 설명
4. **값이 맞나** → 거래정보 표 (원문과 나란히)
5. **누가 무엇을 하나** → 부서별 체크리스트

## 4. 화면별 기능 명세

### S1. 시작·업로드

**목적**: 서비스가 무엇을 해 주는지 알리고, 설명 없이 바로 파일을 올리게 한다.

| 구성 요소 | 기능 | 비고 |
| --- | --- | --- |
| 제목·한 줄 소개 | "영문 송장·발주서를 올리면 한글 표, 쉬운 해설, 부서별 할 일로 정리" | 기획서 한 줄 소개 |
| 업로드 영역 | 끌어다 놓기 + [파일 선택] 버튼. 영역 전체가 클릭 대상 | 키보드로도 선택 가능 |
| 지원 조건 안내 | JPG · PNG · PDF / 1페이지 / 최대 20MB(제안) / 영문 송장·발주서 | 업로드 전에 보이게 |
| 예시 문서 | 정상 송장 · 금액 오류 송장 · 발주서 3종. 누르면 바로 S2로 | 데모 시나리오 3건과 동일 |
| 신뢰 안내 | 사내 서버에서만 처리 / 약 30초 / 보관 기간 | 보관 기간은 팀 결정 필요 |

**상태**

| 상태 | 화면 | 다음 행동 |
| --- | --- | --- |
| 기본 | 업로드 영역 + 예시 문서 | 파일 선택 |
| 끌어다 놓는 중 | 영역 테두리·배경 강조, "여기에 놓으세요" | 놓기 |
| 파일 선택됨 | 파일 칩(이름·크기·형식 확인 ✓) + [분석 시작] + [다른 파일] | 분석 시작 |
| 형식 오류 | 영역 안 인라인 오류: 원인 + 해결 방법 | 다른 파일 선택 |
| 용량 초과 | 인라인 오류: "20MB 이하로 줄여 주세요" | 다른 파일 선택 |
| 여러 파일 | 인라인 안내: "한 번에 한 문서만 올릴 수 있어요. 첫 파일만 선택했어요." | 계속 |

**규칙**
- 형식·용량 검사는 업로드 전에 브라우저에서 한다(서버 왕복 없이 즉시).
- 여러 페이지 PDF는 서버에서 확인해 S4(지원하지 않는 문서)로 보낸다. 첫 페이지만 처리하는 방식은 팀 결정 필요.
- [분석 시작]을 누른 뒤에는 버튼을 비활성화해 중복 전송을 막는다.

### S2. 처리 중

**목적**: 기다리는 30초 동안 "지금 무엇을 하는지"와 "얼마나 남았는지"를 보여 준다.

| 구성 요소 | 기능 |
| --- | --- |
| 문서 미리보기 | 올린 문서의 썸네일. 읽는 중임을 보여 주는 스캔 효과 |
| 단계 표시 (4단계) | ① 문서 읽기 → ② 금액 검산 → ③ 용어 확인·번역 → ④ 해설·할 일 작성. 완료 ✓ / 진행 중 / 대기 3가지 상태 |
| 단계별 중간 결과 | 단계가 끝날 때마다 찾은 값 일부를 칩으로 보여 줌 (예: "INV-24-0917", "GBP 15,691.93") |
| 경과 시간 | "12초 경과 · 보통 30초 안에 끝나요" |
| 취소 | [취소] → 확인 없이 S1로. 서버 작업도 중단 요청 |

**규칙**
- 단계 상태는 백엔드가 알려 주는 값을 쓴다(폴링 또는 스트리밍). 백엔드가 단계를 못 알려 주면 시간 기준으로 표시하되 마지막 단계에서 멈춰 기다린다(가짜 완료 금지).
- 30초를 넘으면 "평소보다 오래 걸리고 있어요" 안내를 추가한다. 60초(제안)를 넘으면 S4(시간 초과)로 간다.
- 브라우저 탭 제목에 진행 상태를 표시한다(예: "② 금액 검산 중 · TradePilot").

### S3. 결과

**목적**: 핵심 질문 3개에 답하고, 사용자가 원문과 대조해 검증할 수 있게 한다.

#### R1. 상단 바

| 요소 | 기능 |
| --- | --- |
| 파일 이름 | 올린 파일 이름 |
| 문서 종류 배지 | 상업 송장 / 견적 송장 / 발주서 |
| 처리 결과 | "18.4초 · 처리 완료 ✓" (성능 기준 30초 증거) |
| 구분 범례 | "표 = 문서에서 읽은 값 / ✦ = AI가 쓴 글" |
| [새 문서] | S1로 (현재 결과는 사라진다는 안내) |

#### R2. 요약 (무슨 문서인가)

| 카드 | 송장 | 발주서 |
| --- | --- | --- |
| 금액 | 총액(통화 포함). 원화 환산은 추가 검토 항목 | 발주 총액 |
| 핵심 기한 | 결제 기한 + D-day 배지 | 최종 선적일(또는 납기일) + D-day |
| 거래 당사자 | 보내는 쪽(국가) → 받는 쪽(국가) | 발주처(국가) → 공급사(국가) |
| 검산 결과 | "검산 통과 ✓" 또는 "확인 필요 N건" | 같음 |

D-day 색 규칙: 지남(빨강) / 7일 이내(주황) / 그 외(회색). 기한이 문서에 없으면 "문서에 없음"(회색).

#### R3. 확인 필요 (이상한 곳은 없나)

| 요소 | 기능 |
| --- | --- |
| 배너 | 문제 건수와 가장 심각한 문제 제목. 문제가 없으면 배너 없음 |
| 문제 카드 | 심각도(오류/주의) · 제목 · 한 줄 설명(무엇이 왜) · [표에서 보기] |
| [표에서 보기] | 거래정보 표의 해당 칸으로 이동해 강조, 원문 위치도 함께 강조(좌표가 있을 때) |

**심각도 기준**

| 심각도 | 조건 예시 | 표시 |
| --- | --- | --- |
| 오류 | 품목 합계 ≠ 소계, 소계+운송비+세금 ≠ 총액, 단가×수량 ≠ 줄 금액 | 빨강 |
| 주의 | 필수 필드 누락(결제 기한 등), 조건 모순(Net 15인데 기한이 30일 뒤), 판독 신뢰도 낮음 | 주황 |
| 안내 | 선택 필드 없음(Incoterms 없음 등) | 표의 "문서에 없음"으로만 표시, 배너에 올리지 않음 |

**문구 규칙**: "무엇이 / 얼마나 / 그래서 무엇을" 순서. 예: "품목·운송비·세금을 더하면 15,691.93 GBP인데 문서에는 15,961.93 GBP로 적혀 있어요(차이 270.00). 송금 전에 거래처에 정확한 금액을 확인하세요."

#### R4. 원문 보기

| 요소 | 기능 |
| --- | --- |
| 원문 이미지 | 왼쪽 고정(스크롤해도 따라옴). 페이지 표시 1/1 |
| 확대·축소·맞춤 | [−] [+] [화면 맞춤], 드래그로 이동 |
| 위치 강조 | 표의 칸에 마우스를 올리면 원문의 해당 위치 강조 (좌표 필요, §7 결정 사항) |
| 크게 보기 | 원문을 화면 전체로 열기 |

#### R5. 쉬운 해설 (무슨 뜻인가)

| 요소 | 기능 |
| --- | --- |
| 해설 문단 | 3~5문장. 해설 규격: ① 누가 누구에게(국가) ② 무엇을 ③ 무슨 문서인지 ④ 금액 구성 → 총액 ⑤ 그래서 할 일 |
| AI 표시 | "✦ AI 작성" 라벨 + "숫자는 문서 값 그대로" 안내 |
| 용어 강조 | 해설·표 속 무역 용어에 점선 밑줄. 마우스를 올리거나 포커스하면 설명 카드 |
| 용어 목록 | "이 문서에 나온 용어 N개": 한국어 (원문) + 쉬운 설명. 용어집 미등록 표현은 따로 표시 |
| 확인 필요 반영 | 검산 오류가 있으면 해설도 단정하지 않고 "확인 필요"로 안내 |

**용어 설명 카드**: 제목 "한국어 (원문)" · 설명 1~2문장 · 출처(용어집). 미등록이면 "용어집에 없는 표현이라 직역했어요. 설명은 제공하지 않아요."

#### R6. 거래정보 표 (값이 맞나)

| 묶음 | 송장 항목 | 발주서 항목 |
| --- | --- | --- |
| 문서 정보 | 문서번호, 발행일, 통화, 송장 종류 | 발주번호, 발행일, 통화 |
| 당사자 | 발행사, 청구처, 배송지 | 발주처, 공급사, 납품처 |
| 품목 | 품목코드, 품명(번역 + 원문), 수량, 단가, 할인, 줄 금액 | 같음 + 요청 사항 |
| 금액 | 소계, 할인, 운송비, 세금(줄별), 총액 + 검산 표시 | 같음 |
| 결제·인도 조건 | 결제 기한, 결제 조건, 결제 방식, 계좌(은행·IBAN·SWIFT), 인도조건(Incoterms), 선적항·도착항 | 납기일, 최종 선적일, 운송사, 결제 조건 |
| 비고 | 비고 번역 + 원문 | 같음 |

**칸 표시 규칙**

| 값 상태 | 표시 |
| --- | --- |
| 읽음 | 한국어 값 + 아래 작은 글씨로 원문 (번역된 값만) |
| 용어집 용어 | "한국어 (원문)" + 점선 밑줄(설명 카드) |
| 용어집 미등록 | 직역 + "용어집 미등록" 배지 |
| 문서에 없음 | 회색 "문서에 없음" (오류 아님) |
| 검산 오류·주의 | 칸 강조 + 문제 아이콘, 확인 필요 카드와 연결 |
| 계산값 | 문서 값과 계산 값을 함께 표시 (예: 문서 15,961.93 / 계산 15,691.93) |

- 회사명·주소·문서번호는 번역하지 않는다(국가명만 한국어).
- 금액은 오른쪽 정렬, 같은 자릿수 폭 숫자, 통화 코드 표시.
- 품목이 많으면(10줄 초과) 처음 10줄만 보이고 [모두 보기].

#### R7. 부서별 체크리스트 (누가 무엇을 하나)

| 요소 | 기능 |
| --- | --- |
| 진행 요약 | "9개 중 2개 완료" |
| 필터 | 전체 / 중요 / 기한 있는 것 |
| 부서 섹션 | 경리 · 구매 · 생산 · 물류 (순서 고정). 섹션 제목 옆 남은 개수 |
| 항목 | 체크박스 · 할 일(동사로 끝나는 한 문장) · 근거(어느 칸에서 나왔는지) · 기한 칩(D-day) · 중요 태그 |
| 근거 연결 | 근거를 누르면 표의 해당 칸으로 이동 |
| 빈 부서 | "이 문서에는 생산 부서 할 일이 없어요" |
| 확인 필요 연결 | 검산 오류가 있으면 관련 항목에 "확인 필요" 태그, 맨 위로 |

- 체크 상태는 이 화면에서만 유지한다(새 문서를 올리면 사라짐). 저장·공유는 MVP 제외.
- 체크리스트 내용은 LLM이 만들지만, 금액·날짜는 코드가 채운다(P1).

### S4. 오류

**목적**: 무엇이 잘못됐는지, 무엇을 하면 되는지 알려 주고 앱을 계속 쓸 수 있게 한다.

| 오류 | 원인 문구 | 해결 문구 | 주 버튼 | 보조 버튼 |
| --- | --- | --- | --- | --- |
| 판독 불가 | 문서 글자를 읽지 못했어요 | 흐리거나 기울어진 스캔일 수 있어요. 더 선명하게 다시 스캔해 주세요 | 다시 올리기 | 예시로 해 보기 |
| 문서 종류 아님 | 송장이나 발주서가 아닌 것 같아요 | 영문 상업 송장·발주서만 지원해요 | 다시 올리기 | 지원 문서 보기 |
| 여러 페이지 | 2페이지 이상인 문서예요 | 지금은 1페이지 문서만 지원해요. 첫 페이지만 따로 저장해 올려 주세요 | 다시 올리기 | — |
| 시간 초과 | 처리 시간이 너무 오래 걸렸어요 | 서버가 바쁠 수 있어요. 잠시 후 다시 시도해 주세요 | 다시 시도 (같은 파일) | 다른 파일 올리기 |
| 서버 오류 | 처리 중 문제가 생겼어요 | 다시 시도해도 같으면 담당자에게 알려 주세요 (오류 코드 표시) | 다시 시도 | 다른 파일 올리기 |
| JSON 파싱 실패 | (사용자에게는 서버 오류와 같게) | 같음, 로그에만 상세 기록 | 다시 시도 | — |

- 사과하지 않고 원인·해결만 쓴다. 기술 용어(JSON, VLM)는 쓰지 않는다.
- 업로드 전 검증 오류(형식·용량)는 S4로 가지 않고 S1 안에서 인라인으로 보여 준다.

## 6. 화면이 필요로 하는 데이터 (W-02 스키마 회의 제안)

현재 설계서 부록 A의 VLM 스키마에 더해, 화면을 그리려면 백엔드가 아래 형태의 **결과 JSON**을 한 번에 돌려주면 좋다.

```json
{
  "meta": { "file_name": "", "doc_type": "invoice|purchase_order", "invoice_kind": "commercial|proforma|null",
            "processing_ms": 18400, "pages": 1 },
  "summary": { "total": { "amount": 15691.93, "currency": "GBP" },
               "key_date": { "kind": "due_date|latest_shipment_date|delivery_date", "value": "2024-10-21",
                             "estimated": false, "d_day": 7 },
               "from": { "name": "", "country_ko": "" }, "to": { "name": "", "country_ko": "" } },
  "issues": [ { "id": "total_mismatch", "severity": "error|warning", "title": "", "message": "",
                "fields": ["common.totals.total"], "values": { "document": 15961.93, "computed": 15691.93 } } ],
  "fields": [ { "path": "invoice.payment_terms", "group": "payment", "label_ko": "결제 조건",
                "value_ko": "30일 이내 지급 (Net 30)", "value_raw": "Net 30", "status": "ok|missing|issue|unregistered",
                "term_ids": ["term_net_terms"], "bbox": null } ],
  "items": [ { "sku": "", "desc_ko": "", "desc_raw": "", "qty": 0, "unit": "", "unit_price": 0,
               "discount_rate": null, "line_total": 0, "status": "ok|issue" } ],
  "explanation": { "text": "", "term_spans": [ { "start": 0, "end": 0, "term_id": "" } ] },
  "terms": [ { "id": "", "ko": "", "raw": "", "explain": "", "registered": true } ],
  "checklist": [ { "dept": "finance|purchasing|production|logistics", "text": "", "due": "2024-10-21",
                   "important": true, "needs_check": false, "source_fields": ["invoice.due_date"] } ]
}
```

- `bbox`(원문 좌표)는 지금 VLM 출력에 없다. 있으면 R4 위치 강조가 가능하고, 없으면 `null`로 두고 강조를 끈다.
- `issues[].fields`, `checklist[].source_fields`가 있어야 "표에서 보기", "근거 연결"이 동작한다.
- 처리 중 단계 표시를 위해 `GET /jobs/{id}` 같은 상태 조회(단계 번호, 중간 결과)가 필요하다.

## 8. 결정이 필요한 사항 (12.01~12.03 W-02 회의)

1. **원문 좌표(bbox)**: VLM이 필드별 좌표를 낼지. 내지 않으면 R4 위치 강조는 제외.
2. **처리 단계 알림 방식**: 백엔드가 단계 진행을 알려 줄 수 있는지(폴링/SSE). 안 되면 시간 기반 표시.
3. **업로드 보관 기간**: 시연 후 삭제 / 24시간 / 즉시 삭제 중 선택.
4. **여러 페이지 PDF**: 거부할지, 첫 페이지만 처리할지.
5. **D-day 기준일**: 시연 날짜를 고정할지, 실제 오늘 날짜를 쓸지(데이터셋 날짜가 2024년이라 실제 날짜면 모두 "지남").
6. **체크리스트 부서**: 경리·구매·생산·물류 4개로 고정할지, 문서마다 필요한 부서만 보일지.
7. **용량 제한**: 20MB 제안.
