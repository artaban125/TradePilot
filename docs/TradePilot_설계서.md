# TradePilot 설계서 (초안 v0.1)

> 작성 기준: 노션 「Vision + NLP/LLM 통합 프로젝트 설계서 템플릿」 + 기획보고서 Must(FR-01~FR-04) + 지금까지의 사전 테스트와 설계 논의
> 작성일: 2026.11.26 / 상태: **팀 상의용 초안**, 12.03 설계 동결 목표
> 표기: `(제안)` = 팀 확인 필요, `❓` = 결정 필요, `✅` = 사전 테스트로 확인된 사실
>
> 템플릿은 "문서 기반 RAG 챗봇"을 기준으로 쓰여 있어서, 우리 과업(문서 이미지 → 구조화 → 해설)에 맞게 항목 이름을 일부 바꿨습니다. 바꾼 곳에는 *(우리 과업에 맞게 변경)*이라고 적었습니다.

### 1. 과업과 입출력 명세

| 항목 | 작성 기준 | 우리 팀 결정 |
| --- | --- | --- |
| 과업 *(우리 과업에 맞게 변경)* | FAQ / 문서 기반 RAG / 요약 / 학습 지원 | **문서 이해 + 구조화 + 쉬운 해설**. 영문 무역 문서 이미지에서 필드를 추출하고, 검산한 뒤 한글 표·해설·부서별 체크리스트를 생성 (질의응답 챗봇은 아님) |
| 대상 사용자 | 사용자 유형과 대표 질문 | 무역 전담 인력이 없는 국내 중소기업 실무자. 대표 질문: "이 서류가 무슨 내용이야?", "얼마를 언제까지 어디로 보내야 해?", "누가 무엇을 해야 해?" |
| 입력 | 질문, 대화 이력, 첨부 문서 | 영문 인보이스·발주서(PO) 1건: 스캔 이미지(JPG/PNG), 스캔 PDF, 전자 PDF. 단일 페이지 우선 |
| 지식원 | PDF, TXT, FAQ 등 | 무역 용어사전(YAML), 문서 종류 안내, 조건별 대응 규칙, 해설 모범 예시 (일반 지식만, 개별 거래 문서는 넣지 않음) |
| 출력 | 답변, 출처, 확인 불가 안내 | ① 한글 거래정보 표(문서 정보·당사자·품목·금액·결제/인도 조건) ② 쉬운 해설 문단 ③ 부서별 체크리스트(경리·구매·생산·물류) ④ "확인 필요" 경고(검산 불일치·누락) ⑤ 원문 이미지 대조 |
| 제외 범위 | 실시간 검색, 계정, 음성, 파인튜닝 등 | 통관·관세 신고 자동화, ERP·회계 연동, 영어 외 문서, 모델 파인튜닝, 다중 페이지 문서(시간 여유 시 검토), 외부 클라우드 API |
| 예외 | 빈 입력, 검색 실패, 모델 실패 | 지원하지 않는 파일 형식·용량 초과, 송장·발주서가 아닌 문서, 판독 불가 이미지, JSON 파싱 실패, 검산 불일치, 모델 호출 실패·시간 초과 |

**처리 흐름 (확정 방향)**

```
[1] 입력 분기      전자 PDF → 페이지 이미지 + pdfplumber 텍스트(힌트)
                   스캔 PDF / 이미지 → 페이지 이미지
[2] VLM 추출       페이지 이미지 (+ 텍스트 힌트) → 영문 JSON (스키마 고정)
[3] 코드 검증       날짜·금액 정규화, 품목·세금·총액 검산, 누락 필드, D-day 계산
[4] 번역·해설       라벨 고정 번역 + 용어사전 치환 + LLM(품명·자유 문장 번역, 해설, 체크리스트)
                   └ RAG: 용어사전·대응 규칙·해설 예시 검색
[5] 화면            고정 HTML 템플릿에 JSON을 채움 (LLM이 HTML을 만들지 않음)
```

### 2. 데이터·문서 설계

#### 2.1 추출 평가용 문서 데이터

| 항목 | 확정할 내용 | 우리 팀 결정 |
| --- | --- | --- |
| 문서 출처 | 문서명, URL·소유자, 라이선스, 개정일 | Hugging Face `AyoubChLin/Company-document-dataset-v2`, Apache-2.0, 버전 고정 `0e9f5198…` ✅ / 합성 무역 문서(팀 자체 생성) |
| 규모 | 문서 수, 페이지 수, 질문 유형 | 개발용: 기존 평가셋 송장 50 + 발주서 50 (1페이지, 스캔·PDF·정답 포함) ✅ / 고정 평가셋: 송장 15 + 발주서 15 (기획보고서 기준, 개발용과 분리) / 오류 탐지용: 금액 오류 주입 20건 / 합성 무역 문서 (제안) 30건 |
| 파싱·정제 | 텍스트 추출, 인코딩, 표·노이즈 처리 | PDF → 150 dpi 이미지, 전자 PDF는 pdfplumber 텍스트 추출. 정답 JSON은 문서에 실제 인쇄된 값만 채점 대상으로 사용 ✅ |
| 정답 형식 | (추가 항목) | 데이터셋 `extracted_data`를 우리 스키마(부록 A)로 변환한 JSON |
| 누수 방지 | 평가 질문을 튜닝에 재사용하지 않음 | 고정 평가셋 30건은 프롬프트 예시·개선 실험에 쓰지 않고 최종 평가 때만 1회 사용. test split에서 seed 고정으로 추출 |
| 보안·권한 | 개인정보, 접근 권한, 보존 | 개발·평가는 공개 합성 데이터만 사용. 업로드 문서는 서버 로컬에만 저장하고 시연 후 삭제 (제안) |

#### 2.2 RAG 지식원 *(템플릿의 "문서·청킹·임베딩" 항목)*

| 항목 | 확정할 내용 | 우리 팀 결정 |
| --- | --- | --- |
| 지식 종류 | (추가 항목) | ① 용어사전 100~150개 ② 문서 종류 안내 3~5개 ③ 조건별 대응 규칙 40~60개 ④ 해설 모범 예시 10~20개 |
| 출처 | 문서명, 라이선스 | 팀 작성 무역 용어 보강안(인코텀즈 2020, HS 코드, 결제조건 등 약 90개 항목), 공공데이터포털 무역 단어 데이터(후보, 라이선스 확인 필요 ❓) |
| 청킹 | 크기, overlap, 메타데이터 | **항목 1개 = 청크 1개** (용어 하나, 규칙 하나). 긴 문서를 자르지 않으므로 overlap 없음. 메타데이터: `id, type, doc_types, keys, source` |
| 임베딩 | 모델명, 차원, 한국어 지원 | `BAAI/bge-m3` (다국어, 1024차원) (제안) |
| 인덱스 | FAISS / Chroma, 저장 경로 | Chroma (로컬 파일 저장) (제안). 원본 YAML은 Git 관리, 변경 시 인덱스 재생성하고 버전 기록 |
| 저장 형식 | (추가 항목) | 용어사전은 **YAML/CSV 파일 하나를 번역과 RAG가 함께 사용** (SQLite 사용 안 함). SQLite는 운영 기록(수정 이력, 사전에 없는 용어)에만 사용 (제안) |

**용어사전 항목 예시**

```yaml
- id: term_net_terms
  keys: ["Net 15", "Net 30", "net 30 days", "payment due in 30 days"]
  ko: 외상 지급 기한
  display: "{N}일 이내 지급 (Net {N})"
  explain: 송장을 받은 날부터 정해진 날수 안에 돈을 보내라는 뜻입니다.
  doc_types: [invoice, purchase_order]
  source: 무역 실무 일반
```

### 3. Vision 모델 및 LLM·RAG 아키텍처 설계

| 항목 | 결정 사항 | 선정 근거 |
| --- | --- | --- |
| Vision 모델 *(추가)* | `Qwen/Qwen2.5-VL-7B-Instruct`, bf16 (RTX 4090) | 사전 테스트(평가셋 100건, 4090 bf16): 송장 98.7~99.7%, 발주서 88.7~93.1%, 약 10초/건, 최대 GPU 메모리 16.2 GB ✅ |
| Vision 비교 후보 | InternVL3-8B | 기획보고서 후보. 기준선 단계에서 같은 평가셋으로 1회 비교 (제안) |
| 기준선 | 검색 없는 직접 LLM 답변 | ① VLM: 이미지만 입력한 추출 결과 ② 해설: RAG 없이 JSON만 주고 LLM이 해설 → RAG 적용 결과와 비교 |
| 생성 모델 | 로컬 LLM 이름·버전 | **비교 평가 후 결정 (12.09)**. 후보: `LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct`, `A.X 4.0 Light` | 같은 입력 JSON·프롬프트로 비교: 해설 필수 항목 포함률, 숫자 보존율, 한국어 자연스러움(5점), 생성 시간·GPU 메모리. 두 모델 모두 교육 과제 범위에서 라이선스 문제 없음 (EXAONE은 비상업 라이선스라 보고서에 명시) |
| 검색 방식 | 임베딩 / 키워드 / 하이브리드 | **하이브리드**: JSON 칸 값(Net 15, FOB 등)은 키워드 매칭, 검산 결과 상황은 규칙 ID 직접 조회, 자유 문장(비고·요청 문구)만 벡터 검색 |
| Top-k | 후보 수, 점수 기준 | 벡터 검색 top-3, 유사도 기준값은 기준선 후 결정. 키워드 매칭 결과는 전부 포함 |
| 프롬프트 | 역할, 근거 우선, 거절 규칙 | 숫자·고유명사는 JSON 값을 그대로 쓰고 바꾸지 않음, 문서에 없는 내용은 쓰지 않음, 용어는 사전 번역 사용 (5장) |
| 생성 설정 | temperature, max tokens | VLM: temperature 0(greedy), 최대 2,048 토큰 / LLM: temperature 0.2, 해설 최대 400자 (제안) |
| 대화 이력 | 미지원 / N턴 / 요약 | **미지원** (문서 1건 단위 처리) |
| 개선 실험 | 1~2개 | ① VLM: 전자 PDF 텍스트 힌트 유무 (사전 테스트에서 효과 확인 ✅), 발주서 누락 필드 프롬프트 수정 ② 해설: RAG 유무 비교 |
| 최종 선택 | 품질·충실성·지연·비용 | 12.09에 고정 기준(4장)으로 결정 |

**모델 로딩 방식**
- RTX 4090(24 GB)에서 VLM(bf16, 최대 16.2 GB ✅)과 LLM(7~8B, 4-bit 약 5~6 GB 추정)을 **동시에 올려 두는 방식**을 기본으로 한다. 모델을 다시 불러오는 시간이 없어진다.
- 메모리가 부족하면 VLM 추론 → 메모리 해제 → LLM 로딩 순서의 **순차 로딩**으로 바꾼다. 12.10 성능 측정에서 확정한다.

### 4. 평가 설계

| 평가 영역 | 지표 | 함께 확인할 사례 |
| --- | --- | --- |
| 필드 추출 *(추가)* | 핵심 필드 F1 (필드 그룹별: 기본정보·당사자·품목·금액·조건) | 일/월 뒤바뀜, 세금 두 줄 합산 오류, 발주서 요청 문구·납품처 누락 (사전 테스트 실패 유형 ✅) |
| 검증 정확도 *(추가)* | 금액 오류 탐지율, 오탐률 | 정상 문서를 오류로 판정하는 경우 |
| 번역 충실성 | 숫자·코드·고유명사 보존율(목표 100%), 용어 정확도 | 금액이 바뀐 해설, 사전과 다른 번역 |
| 해설·체크리스트 품질 | 필수 항목 포함률(당사자·금액 흐름·결제 방법·기한), 사람 평가(5점) | 누락·오해·잘못된 지시 |
| 검색 품질 | Recall@3 (용어·상황 질의 50개) | 관련 용어 누락 |
| 시스템 성능 | 문서당 처리 시간(평균·중앙값), 최대 GPU 메모리 (측정 GPU를 함께 기록) | 30초 초과 |
| 안전성 | 문서 속 지시문(프롬프트 인젝션) 무시 여부 | "Ignore previous instructions" 같은 문구가 비고에 들어간 문서 |

| 평가 항목 | 우리 팀 결정 |
| --- | --- |
| 고정 평가셋 | 추출: 송장 15 + 발주서 15 / 검증: 정상·오류 문서 20건 / 해설: 고정 평가셋 30건의 해설 결과 |
| 정답 근거와 평가자 | 추출·검증은 정답 JSON과 자동 비교. 해설·체크리스트는 팀원 2명이 체크리스트로 평가 (평가자 간 차이 기록) |
| 핵심 지표와 목표값 | 필드 F1 90% 이상 / 금액 오류 탐지율 90% 이상 / 체크리스트 적절성 85% 이상 / 처리 시간 30초 이내 (기획보고서 성공 기준) |
| 기준선·개선 비교 조건 | 같은 평가셋·같은 해상도(최대 1.6M 픽셀)·같은 모델 버전에서 비교 |
| 반복 실행·모델 설정 | VLM은 greedy라 1회, LLM은 3회 실행해 편차 기록 (제안) |
| 성공·실패 사례 기록법 | 문서 ID별 결과 JSON과 원문 이미지 경로를 함께 저장, 실패 유형 태그 부여 (예: `date_swap`, `missing_field`) |

> 개발 중에는 개발용 50+50건으로 개선하고, 고정 평가셋 30건은 반복 튜닝에 쓰지 않는다. 수치 목표는 기준선 실행 후 다시 확인한다.

### 5. 프롬프트·검색·응답 설계

| 항목 | 확정할 규칙 | 검증 방법 |
| --- | --- | --- |
| VLM 프롬프트 *(추가)* | 스키마를 그대로 제시, 문서에 인쇄된 값만 추출, 없으면 `null`, 추측 금지, 세금은 줄별로 추출(합산은 코드가 함), 날짜는 원문 그대로 | JSON 파싱 성공률, 필드 F1 |
| 시스템 프롬프트 (LLM) | 역할: 무역 비전문가에게 설명하는 도우미 / 한국어, 쉬운 말 / 해설 3~5문장 / 금지: 숫자 변경, 문서에 없는 사실, 법률·세무 단정 | 정상·경계 문서 |
| 문서 검색 | 항목 단위 청크, 키워드 우선 + 벡터 top-3, `doc_type` 필터 | 검색 적중률 |
| 문맥 구성 | 검증된 JSON + 검색된 용어 설명·규칙 + 해설 예시 1~2개, 전체 문맥 4K 토큰 이내 (제안) | 품목이 많은 문서 |
| 숫자 처리 | 금액·날짜·수량은 코드가 형식 변환(예: 15,691.93파운드, 2024년 10월 21일)해서 넘기고 LLM은 그대로 인용 | 숫자 보존 자동 검사 |
| 생성 | temperature·max tokens·타임아웃(LLM 20초) | 반복 테스트 |
| 근거 표시 | 해설 아래에 사용한 용어 설명 표시(예: "Net 15 = 15일 이내 지급") | 용어 대조 |
| 근거 부족 | 필드가 비었거나 검산이 틀리면 해설에 단정하지 않고 "확인 필요"로 안내 | 누락·오류 문서 |
| 입력 방어 | 파일 형식·용량 제한, 문서 속 지시문은 데이터로만 취급 | 악성 문구 문서 |
| 로그 | 업로드 원본·결과는 로컬에만 저장, 계좌번호 등은 로그에 남기지 않음 | 저장 내용 점검 |

**번역 규칙**

| 대상 | 방법 | LLM 사용 |
| --- | --- | --- |
| 칸 이름 (Invoice No., Due Date) | 고정 번역표 | ✕ |
| 숫자·금액·날짜 | 번역 안 함, 코드가 형식만 변환 | ✕ |
| 코드·번호, 회사명·주소 | 원문 유지 (국가명만 한국어) | ✕ |
| 정해진 조건 값 (Net 15, FOB Busan) | 용어사전 치환, "한국어 (원문)" 함께 표기 | ✕ |
| 품명, 자유 문장 | LLM 번역 + 용어사전 강제 적용 + 숫자 보존 검사 | ○ |

**해설 규격 (기준 예시)**
① 누가 누구에게(국가) ② 무엇을(쉬운 말) ③ 무슨 문서인지 ④ 금액 구성 → 총액 ⑤ 그래서 할 일

> "영국 Meridian Components가 미국의 Thomas Anderson에게 자전거 펑크 패치 키트 1개를 팔았다는 청구서입니다. 물건값 1.81파운드에 운송비 0.05파운드, 세금 0.14파운드를 더해 총 2.00파운드입니다. 결제는 이미 신용카드로 끝났으므로 따로 돈을 보낼 필요가 없습니다."

### 부록 A. JSON 스키마 개요 (W-02에서 확정)

공통 뼈대 + 문서 종류별 블록 + 무역 블록 구조입니다. VLM에는 해당 문서 종류의 스키마만 보여 줍니다.

```json
{
  "doc_type": "invoice | purchase_order",
  "invoice_kind": "commercial | proforma | null",
  "common": {
    "number": "", "issue_date": "", "currency": "",
    "issuer": { "name": "", "city": "", "country": "" },
    "items": [ { "sku": "", "description": "", "quantity": 0, "unit": "",
                 "unit_price": 0, "discount_rate": null, "tax_rate": null, "line_total": 0,
                 "hs_code": null, "country_of_origin": null } ],
    "totals": { "subtotal": 0, "discount_total": null, "freight": null,
                "taxes": [ { "label": "", "amount": 0 } ], "total": 0 }
  },
  "invoice": { "bill_to": {}, "ship_to": {}, "due_date": "", "payment_terms": "", "payment_instructions": "" },
  "purchase_order": { "vendor": {}, "deliver_to": {}, "delivery_date": "", "instructions": "", "carrier": "" },
  "trade": { "incoterms": { "rule": null, "place": null },
             "payment": { "method": null, "bank": { "swift": null, "iban": null } },
             "transport": { "port_of_loading": null, "port_of_discharge": null, "latest_shipment_date": null } },
  "other_fields": {}, "other_text": []
}
```

- 견적서(quote)는 시간이 남으면 `invoice` 블록에 `valid_until`을 더해 확장한다.
- 무역 블록의 상세 필드 목록은 팀 내부 자료인 무역 용어 보강안 9장을 기준으로 W-02에서 확정한다.
